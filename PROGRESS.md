**2. The format grows to a song** — done, with tests (SPEC v0.8, §4.4 and §5)
- Lee's decisions (2026-11-12):
  - **Time signatures:** a beat is the denominator's note, and positions' third number counts sixteenths within it. Ticks are 960 per quarter note in every signature; tempo is quarter notes per minute; note lengths stay whole-note fractions. Bottom numbers 2, 4, 8 and 16; one signature per song.
  - **Volume and pan** are strings with units, read by a general value-with-unit parser that device parameters reuse in Milestone 4: `"-6dB"`, `"0dB"` (unity), `"-infdB"` (silence); pan `"C"`, `"L1"`–`"L100"`, `"R1"`–`"R100"`, with the pan law written down. Mute and solo are booleans.
- Picked here, within those (SPEC §4.4):
  - The top number of a time signature is 1–32.
  - Volume runs from −96 dB to +6 dB (Tracktion's fader top), in steps of 0.1 dB, or −inf. The writer drops trailing zeros and writes boosts with `+`.
  - Pan is a balance control: at C both channels pass unchanged, and panning lowers the far channel linearly in gain, to silence at L100/R100. Tracktion's laws all boost the near side or lower the centre, so step 6 gets this out of its linear law with a matching volume.
  - A muted track stays silent when soloed.
  - The mix keys are required and always written, like every other key.
- Done:
  - `core/units`: `units::parse`/`format` for any quantity (several units, rounding, `-inf`), `units::volume()`, and `parsePan`/`formatPan`.
  - `notes::Meter` has a numerator and denominator; `parseMeter`; positions and their errors follow the signature ("sixteenth 3 doesn't exist in 6/8: a beat there is an eighth note, so sixteenths are 1-2").
  - Linked clips: `Project::notesFiles` holds each file's notes once, keyed by file; `notesOf`, `clipsUsing`, `clipEnd (project, clip)`. The reader reads a file once and reports its errors once; the writer writes it once.
  - `write_clip` on a linked clip changes the file, so every clip using it; a longer `@length` must fit all of them, and the error names the tightest. The bus's edits and change notices (`NotesChanged`) are per file, and so is `changesTo`. `--watch` watches each file once and sends a save to its first clip.
  - Tracks may have no device. Every clip ends by 1000.1 (`maxSongLengthInBars`), in the reader and in `write_clip`.
  - `"hocket:synth"`, played by 4OSC. An old `"tracktion:4osc"` gets an error saying it's now `"hocket:synth"`. The demo is in the new format.
  - `EditSync` builds any signature: ticks become Tracktion beats by the signature's ticks per beat (Tracktion's default `lengthOfOneBeatDependsOnTimeSignature()` makes its beats the denominator's note and its BPM quarter notes per minute, `tracktion_Tempo.h`). Render tests confirm notes sound on time in 6/8, 7/8, 3/2, 5/16 and 3/4.
  - The overview shows each track's mix, what a beat is outside x/4, and which clips are linked; `read_clip` and `write_clip` name linked clips. `write_clip`'s description has the new position rules, so `hocket-mcp` was reinstalled.
  - Parser messages no longer say "Milestone 0": they say when the feature comes (`@swing`/`@ch` Milestone 3, controllers Milestone 6).
- Volume, pan, mute and solo reach the Edit since step 6, part 2.

**3. Drum tracks in the format** — done, with tests (SPEC v0.9, §4.4 and §5.2)
- Lee's decisions (2026-11-12):
  - The map lives on the track in `project.json`, so a project reads and validates without any kit present. One list of standard names on General MIDI's notes (SPEC §5.2), kept as written.
  - A drums track is `"type": "drums"`, with a required `"drumMap"` of names to MIDI note numbers (`"kick": 36`). One note per name and one name per note.
  - A note the map names is always written by its name (`D2` becomes `snare`). A drum name on a track with no map is an error that says so.
  - A file linked into several tracks: every note in it has the same name in each track's map, or none does.
  - Map names can't look like a lowercase note name (`c2`), a controller, `v` and a number (a velocity), or `ch` and a number (a MIDI channel).
  - On a drums track, `write_clip`'s result lists the notes the map doesn't name, and says they only sound if the kit has a piece there.
- Picked here, within those:
  - Names are lowercase letters and digits in words joined by single hyphens, starting with a letter (so the parser can tell a name from a position or a number), at most 32 characters.
  - In `project.json`, `drumMap` comes between `devices` and `clips`, by note; a drum sampler's `kit` after its `type`. Kit names are lowercase and hyphenated, like clip files, since a kit is a folder (SPEC §8.4).
  - `hocket:drum-sampler` goes on drums tracks only; `hocket:synth` on either type. A map may be empty.
  - A named note's spelling isn't kept: the model spells it sharp on a black key, so the parsed clip is the same however it was written.
  - A track with no drum map names nothing, so a file shared between a `"midi"` track and a drums track is fine only while the map names none of its notes.
- Done:

  - `notes::parse` and `notes::write` take the track's map. Errors for drum names: an unknown one gets "did you mean" and, in the first such error only, the map's names; `Kick` is told to be lowercase; a number like `36` is told its name and note name (on any track).
  - `project.json`: drums tracks and their maps, `hocket:drum-sampler` and its `kit`, each with their own required keys, and errors for a `drumMap` or `kit` where it doesn't belong. A broken or missing map stops its track's clip files being read, rather than piling up errors in them, and an error says which clips weren't checked, so a short list isn't taken to mean they're fine.
  - The linked-file check in the reader and in `write_clip`, naming the notes, the names and the tracks (`project::drumNameConflicts`). Files are written with their first track's map (`drumMapOfFile`).
  - The overview shows a drums track's kit and map (`kick=36, snare=38`); `read_clip` says where the names come from; `write_clip`'s description has drum names. The fingerprint changed, so `hocket-mcp` was reinstalled.

**5. Sync: tracks and clips** — planned with Lee on 2026-11-12
- Lee's decisions (2026-11-12):
  - **When a change ends the song before the playhead** (the last clip removed while it plays, say), the playhead wraps as if the loop had always been that length, landing on the same beat of the bar so the pulse carries on. If that isn't clean in Tracktion, say why, and jump to 1.1 instead. [Claude's note: Tracktion's playhead maps its running sample count into the loop by remainder, which may already do this when playback started at the loop's start. Check its source and test it live.]
  - **Clip changes must be glitch-free.** If adding or removing a track or an instrument can't be made gapless, stop and tell Lee what was measured before working around it.
- How it works (proposed by Claude, approved):
  - `EditSync` keeps Tracktion's tracks by ID, as it does clips, not by their index in the project.
  - Each change notice names a track or clip; `EditSync` brings that one in line with the model as it now is, whatever the notice says, so the order of a command's notices doesn't matter (a clip moved between tracks is "removed", then "added").
  - Handled: tracks added, removed, moved and renamed; instruments added, replaced or removed (a 4OSC made or deleted); clips added, removed, moved, or given a new file; files joining or leaving the project. The assertion that clips never appear or vanish goes.
  - The loop range is recomputed after every structural change.

  3. Live tests, the riskiest first: a clip removed or moved while its note sounds ends that note (Tracktion's `LoopingMidiNode` hands notes on only when the node survives a rebuild, and a removed clip's doesn't); a change to one track doesn't stop or retrigger a held note on another; the playhead wraps when the song gets shorter. `MidiRecorder` moves to the shared test helpers.
     Done (`LiveStructureTests.cpp`), with two fixes the tests called for:
     - **A clip moved on its own track kept its sounding note** until its new start: Tracktion's `LoopingMidiNode` hands a clip's sounding notes to the next graph, and a moved clip keeps its node. A removed clip's node goes, and its notes end. So `syncClip` removes and remakes a clip whose start or track changes; a new `@length` keeps it, so a note held across it isn't cut. A clip moved to another track was already fine.

**7. Hocket's drum sampler, and how kits work** — planned with Lee on 2026-11-17; in SPEC v0.14, §3.3, §5.2, §8.1 and §8.4
- Hocket's first device, a Tracktion plugin type of its own (`PluginManager::createBuiltInType`). It sets the pattern the synth and effects follow in Milestones 4 and 5. Not Tracktion's `SamplerPlugin`, which locks and allocates on the audio thread (Known upstream issues).
- Lee's decisions (2026-11-17):
  - **A note's length is ignored for one-shots.** A hit plays its sample to the end unless a choke group cuts it, and note-offs do nothing. So a stop or a seek (all-notes-off) leaves hits ringing, and so does a clip that ends or is rewritten under a hit. Lengths stay in `.notes`; `write_clip`'s description says a drum's length doesn't change its sound, and that 1/16 is usual.
  - **Choke groups are in the kit's manifest** (`"chokeGroups": [["hat-closed", "hat-pedal", "hat-open"]]`). A hit cuts every sounding hit in its group, its own piece's included; pieces in no group ring over each other. A cut is a 10 ms fade from the cutting hit's sample.
  - **Sample rates:** each piece is converted once to the device's rate, off the audio thread, so the audio thread only copies with a gain; at equal rates nothing is converted, and a hit is bit-exact. JUCE's `WindowedSincInterpolator` won't do: its kernel is the same at any ratio, so converting down doesn't filter. **Use Tracktion's bundled libsamplerate** if `KitLibrary` can reach it cleanly, and add it to DEPENDENCIES.md's "Updating Tracktion" as something to re-check; otherwise write our own windowed sinc, flat to 20 kHz within 0.1 dB, with aliasing at least 90 dB down. Not r8brain.
    - [Claude's check, from the source: Tracktion compiles libsamplerate's C files as C++ inside `namespace tracktion::src` (`tracktion_engine_playback.cpp`), with all three sinc converters on, and the header has no `extern "C"`. Part 2 confirms it links and meets the targets, and times it.]
  - **Headroom, the strict rule:** every piece of a kit struck at once at v127, on a track at 0 dB and C, peaks at −1 dBFS or under (choke groups apply). The sampler adds no gain (at v127, a piece at a level of 0 dB plays its sample exactly), so the kit's levels keep to it; a test renders it for every bundled kit (step 8 brings the first).
    - **Replaced by Lee (2026-11-20, step 8; SPEC v0.19, §8.1 and §8.4):** the heaviest realistic hit, kick, kick2, snare, clap, open hat and crash struck together at v127, peaks at −1 dBFS or under, at 44.1 and 48 kHz; every piece at once is no rule, since the output meter covers it. And a bundled kit's kick at v127 peaks at −12 dBFS, the level every bundled kit matches. With every piece at once as the rule, the electronic kit's kick came out at −19.5 dBFS.
  - **Velocity:** gain = level × (v/127)², General MIDI's default curve (v100 −4.2 dB, v64 −11.9 dB, v28 −26 dB). In one place in the code: Lee judges ghost notes by ear in step 8.
  - **A kit that isn't installed is refused when assigned**, with "did you mean" and the installed kits. A project file naming one still loads (SPEC §8.4).

- How it works (proposed by Claude, approved):
  - **Nothing locks or allocates on the audio thread.** The sampler has three kinds of state:
    - The kit's audio: a read-only object built on the message thread (decoded, converted to the device's rate, each piece's gain, a 128-entry note table, the choke groups as small numbers), handed over through one atomic pointer that the audio thread takes at the start of a block. Each carries a number; the audio thread publishes the oldest one any sounding hit still uses, and the message thread frees only older ones, so hits ring on through a kit change. No `shared_ptr` on the audio thread: the last reference would free memory there, and `std::atomic<std::shared_ptr>` isn't lock-free on MSVC.
    - Voices: a fixed pool of 64, the audio thread's alone. When it's nearly full, the oldest hit fades out to make room, so no hit is dropped and none cut without a fade.
    - Atomic flags: Tracktion's panic or reset fades every hit.
  - MIDI is read from Tracktion's `MidiMessageArray` in timestamp order, through a fixed-size index; no `juce::MidiBuffer` (where 4OSC allocates). Hits start on their exact sample, with timestamps read as 4OSC reads them.
  - Rate-dependent work goes in `initialise()`, which Tracktion runs on the message thread only when no graph is playing the plugin (`Plugin::baseClassInitialise`). Converted kits are cached per rate, so a device reopened at another rate, or a render at one, costs one conversion.
  - The proof: the engine tests replace global `operator new`/`delete` and count allocations made on a thread inside the sampler's audio code, through hits, chokes, a full pool, a kit swap, all-notes-off and panic: zero. The audio code uses no lock types, and its atomics are `static_assert`ed lock-free.
  - **Kits:** `assets/kits/<name>/kit.json` with the samples beside it (SPEC §8.4 has the format), read in core (no JUCE) so `--check`, the bus and the overview know a kit's pieces without loading audio. The build copies the kits to `kits\` next to the programs. A test checks that every bundled kit uses the standard names on the standard notes (SPEC §5.2).
  - `KitLibrary` (engine) loads a kit on the message thread, cached by name and shared by every track using it. Its load time is measured; a loader thread only if it holds up the API noticeably. A broken kit counts as missing, with the reason. `--check` notes a missing kit without failing.
  - The bus reads kit manifests through a small interface, so core stays free of JUCE, and its tests use fakes.
  - `EditSync` creates the sampler for `hocket:drum-sampler`. A change of kit alone goes to the existing plugin, with no graph rebuild. The sync check compares each sampler's kit. `--play`'s "is silent" note goes.

**9. Saving, the recovery copy, and changes made outside Hocket** — planned with Lee on 2026-11-20; in SPEC v0.21, §4.5
- **Lee's decisions (2026-11-20):**
  - **Unused clip files** (Lee's lean, taken as is): a `.notes` file that was in the project, but that no clip uses any more, is moved on save to `unused/`, keeping its path (`unused/clips/verse-2.notes`), numbered if that name is taken (`verse-2-2.notes`). Never deleted; files Hocket never had in the project (never loaded or written by it) are never touched. If an undo brings the clip back, the next save writes it in `clips/` again; the copy in `unused/` stays.
  - **Who can save, and how the person's way back is protected:** any client can save, Claude included (Milestone 1 has no GUI, and step 11's demo song is saved through the API). **Every save keeps the version it replaces**, so no save can lose a version that was saved. **Keep every save** for now (a cap can come in Milestone 9). **Kept saves live inside the project**, in `.hocket/saves/`, so they travel with it.
  - **Each kept save is a complete copy** of the project's text files as they were (`project.json` and every clip file), so any one restores without the others, by the revert command or by hand.
  - **Loading, `--check`, `--watch` and the outside-change check all ignore `.hocket/` and `unused/`.** The repository's example projects keep `.hocket/` out of git (`.gitignore`).
  - **Kept-save folder names are valid on Windows** whatever the author or the save's name contains: `<number> <time> <author>[ <name>]`, with characters Windows refuses (`<>:"/\|?*`, control characters), trailing dots and spaces, and reserved names (`CON`, `NUL`...) replaced or dropped, and cut short to fit; the number keeps them apart. Tested with nasty names, non-ASCII ones included.
  - **SPEC says why text-only copies stay enough once audio arrives** (Milestone 7): audio files are never modified (SPEC §4.3), and every edit lives in `project.json`, so the text says everything; unused audio goes to `unused/`, never deleted, and a revert that names it moves it back.
  - **The `S` key in `--play`'s console** saves as the person: Lee's explicit save while headless.
- The plan (proposed by Claude, approved):
  - **A save command** any client can send; not a history entry. The bus knows whether anything is unsaved: the history position at the last save, so undoing back to it counts as saved. A save can carry a name.
  - **Atomic writes:** each file to a temporary file beside it, then swapped in (in the platform layer: `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` on Windows); clip files first, `project.json` last. Only files whose text changed are written, so unchanged files keep their dates.
  - **Kept saves:** before writing, the version being replaced is copied whole to `.hocket/saves/<number> <time> <author>[ <name>]/`. A **revert** command restores a kept save into the session as one history entry, undoable, validated like a loaded project; a **list** command shows the kept saves (number, time, author, name). The save's result names what it kept ("your previous save is kept as save #4, by Lee, 14:02"), and what moved to `unused/`.
  - **`--new <folder>`:** an empty project (120 BPM, 4/4, no tracks) in a new or empty folder; a folder with anything in it is refused.
  - **The recovery copy:** a few seconds (about 3) after changes stop, the whole project is written atomically to `%LOCALAPPDATA%\Hocket\Recovery\<folder name> <short hash of its path>\`. Removed after a save, or at a clean exit with nothing unsaved; a clean exit with unsaved changes keeps it and says so. Opening a folder whose recovery copy is newer than its files says so, and `--play --recover` loads the copy (as unsaved changes).
  - **Outside changes:** Hocket notes each file's size and modified time whenever it reads or writes it. A save that would overwrite a file changed on disk since then writes nothing and names the file; saving with `overwrite` writes anyway, after keeping the outside version as a kept save. `--watch` covers `project.json` too: a saved change becomes one command replacing the project's structure, checked and undoable like any other.
  - **Tests**, on a non-ASCII folder: a failure mid-save leaves the old files; save, load and save again byte-identical; unused files moved, foreign files untouched; kept saves complete, restorable by hand (load the folder) and by revert, and named validly whatever the author or name; unsaved tracking through undo and redo; the recovery copy written, removed and loaded; outside changes refused, and `overwrite`; `--new`; `.hocket/` and `unused/` ignored by loading, `--check` and `--watch`.

- **Part 1 done (2026-11-20), with tests** (SPEC v0.22 adds the guarantees below to §4.5):
  - **`hocket_storage`** (`src/storage`), a new library: saving needs the platform layer, which links core, so it can't be in `hocket_core`. The bus reaches it through `commands::Storage` (`core/commands/Storage.h`), as it reaches the engine through `Transport`. `storage::ProjectFolder` is the folder; `storage::createProject` is `--new`'s.
  - **A save** compares each file's canonical text with the disk's and writes only those that differ. It writes every new text beside its file first (`<file>.hocket-saving`, through `platform::writeFileToDisk`, which flushes to disk), so a problem writing any of them changes nothing. Then it swaps them in (`platform::replaceFile`: `MoveFileExW`, replace and write-through), clip files first, `project.json` last; if one fails, the files already swapped are put back (a new one is removed), so **a failed save leaves the folder as it was**, and its message says why. A file that's there but can't be read stops the save before anything is written.
  - **`unused/`:** `ProjectFolder` keeps the clip files Hocket has had in the project (loaded, or written by a save). After `project.json` is swapped in, those no clip uses and still on disk are moved (`platform::moveFile`, never over another file) to `unused/<path>`, numbered `name-2.notes` and on when taken. A move that fails is reported and tried again at the next save. A session only knows the files its project had when the folder was opened.
  - **Unsaved tracking:** each history entry has a revision number, never reused (a gesture's merge gives the entry a new one); an open transaction with edits has its own, which the entry it becomes keeps. `hasUnsavedChanges()` compares the current revision with the saved one, so undoing or redoing back counts as saved, and a commit or split of a transaction saved part-way stays saved. It errs towards unsaved: the same change made again, or a gesture saved part-way that leaves that value and comes back to it, counts as unsaved. A gesture that ends where it started, from a save, is saved: it leaves no entry.

  - `notes/`: the `.notes` model, parser and canonical writer. Tracks are `midi` or `drums`, with volume, pan, mute and solo; a drums track has a `drumMap` (`drumMapOf`, and `drumMapOfFile` for a file's), and a drum sampler a `kit`. `drumNameConflicts` says where a linked file's tracks would name its notes differently. A song ends by 1000.1 (`maxSongLengthInBars`). `load` can say before it reads each file (for stamps). `FileStamp`: a file's size and modified time.

The bus holds a catalog (`setKitCatalog`), which assigning a kit checks against.

A command that changes nothing adds no entry. `interruptTransaction`, `openTransaction`, `changesTo` (the entries that changed a clip file's text: its notes, or how they're written); gestures merge into one entry (SPEC §3.1). It keeps the session's transport settings (`transportSettings()`: the loop region, loop on or off, the last seek), checks and words transport commands (`commands/Transport.h`, `TransportCommands.cpp`), and has the engine carry them out; `isPlaying()` asks it.

## Gotchas picked up so far
- **Line endings.** This machine has `core.autocrlf=true`. `.gitattributes` keeps `*.notes`, `*.auto` and `project.json` LF; add any new byte-compared fixture type there. In the Bash tool, `grep $'\r'` reports every line; count CRs with `tr -cd '\r' < file | wc -c`.
  - Checked-out sources are CRLF, but files the Write tool creates are LF, so `git add` warns "LF will be replaced by CRLF". That's harmless: the repository stores LF either way. A script that edits a source file should keep its line endings (read with `newline=''` in Python).
- **Building from the tools.** `cmake` isn't on PATH in the PowerShell tool. Prepend `C:\Program Files\Microsoft Visual Studio\18\Community\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin` to `$env:PATH` in the same command, then use CLAUDE.md's presets. Filter a build's output with `Select-String -Pattern "error|warning C"`: no output means a clean build.
- **Test fixtures** live in `tests/fixtures/` (`HOCKET_FIXTURES_DIR` in the core and storage tests); `examples/` is for projects meant to be played (`HOCKET_EXAMPLES_DIR`).
- **Tracktion sends "all notes off" when play starts** (at sample 0, before the first note-on), so a test that nothing reached a note since it was struck checks the events after the note-on, not every event (`LiveRevertTests.cpp`).
- **Holding a file the way an editor does, in a test:** a `std::ifstream` open on it. The C runtime shares reads and writes but not deletes, so on Windows the file stays readable while `MoveFileExW` can't replace it ("Access is denied."). `platform::FileLock` holds it harder: nothing can even read it.
- **Don't name a helper `quoted`.** Argument-dependent lookup finds `std::quoted` instead (error C2676). The code uses `singleQuoted` / `doubleQuoted`.
- **nlohmann/json** is built with implicit conversions off: write `get<T>()`.
- **Property tests against the bus** must canonicalize their reference copy with `*notes::parse (text).clip`, because the bus stores the parsed clip (spellings filled in), not the text. The parsed clip isn't canonical, though: notes and comments stay where the text had them. To ask whether two clips are the same, compare `notes::write` of each, as the bus does for "changes nothing".
- **doctest has no `GENERATE`** (that's Catch2): loop over a table, with `INFO` for the case.
- **Windows PowerShell 5.1 reads a `.ps1` without a byte order mark as ANSI**, so keep scripts ASCII (`tests/acceptance` builds its non-ASCII folder name from `[char]` codes). And an expression can't continue onto a line that starts with `+`: build the string first.
- **Build time.** JUCE and Tracktion compile once into `hocket_juce`. A clean Release build takes 1 to 2.5 minutes here (2 min 21 s in a fresh clone on 2026-10-30). A fresh clone's time is mostly the submodule download, which varies a lot: 21 minutes on 2026-10-30, but the whole `-FreshClone` step took 4.7 min on 2026-11-06. The download is about 1 GB. The parallel build needs several GB of free memory: a run on 2026-11-06 was killed while ComfyUI held a model in memory (a `python` process using 9.6 GB).
- **Tracktion's first MIDI scan.** Before playing, call `engine.getDeviceManager().rescanMidiDeviceList()` and run the message loop briefly (`runDispatchLoopUntil (100)`), as `--play` does. Otherwise the scan lands 4 s after startup and stops playback. The engine tests never see this: the hosted device has `useMidiDevices = false`. A Tracktion bug, not reported (Known upstream issues); whether it's still needed is checked on every Tracktion update (DEPENDENCIES.md).
- **`JUCE_MODAL_LOOPS_PERMITTED=1`** (set on `hocket_juce`) makes `MessageManager::runDispatchLoopUntil` available. `runDispatchLoop` can only run once per process: after `stopDispatchLoop` it returns at once.
- **One Tracktion `Engine` at a time.** The engine tests share `testing::testEngine()`, which never opens a real device and keeps its settings in a temp folder. A `FakeAudioDevice` must be opened before the `EditSync` whose Edit plays on it.
- **Live tests and graph rebuilds.** Tracktion applies a change to the playback graph on a 1 ms message-thread timer. In single-threaded tests, call `edit.dispatchPendingUpdatesSynchronously()` to apply it at an exact point.
- **4OSC isn't deterministic** from run to run (oscillator phase), so compare loudness between runs, not samples.
- **The real-time harness** (`tests/engine/StressTests.cpp`). An `AudioThread` (a JUCE real-time thread) calls `FakeAudioDevice::playBlock` at a sound card's pace, while the test thread runs `runDispatchLoopUntil (1)` and sends commands; it behaves like the app.
  - `playBlock` renders into a buffer allocated up front: JUCE's `AudioBuffer::setSize` reallocates whenever it grows, even with `avoidReallocating` (that only helps when shrinking), so growing `output()` on every block would swamp the timing.
- **Engine tests that run the message loop** receive whatever Tracktion has posted before, and handling a device update stops the transport. A test that ran after another test's device was closed stopped playing within two blocks. `FakeAudioDevice` now handles pending messages when it opens and closes.
- **Tracktion has two MIDI clip nodes.** A clip that can use a proxy sequence (`MidiClip::canUseProxy()`, true by default) plays through `MidiNode`, which keeps no note state across graph swaps, so a rewrite that changes a sounding note leaves it stuck. With `setUsesProxy (false)` it plays through `LoopingMidiNode`, which hands its sounding notes to the next graph and ends the ones the rewrite took away (`createNodeForMidiClip`, `tracktion_EditNodeBuilder.cpp:676`). `EditSync` turns the proxy off for that reason, until upstream's `MidiNode` hands its notes over too (checked on every Tracktion update, DEPENDENCIES.md). Read the node that actually plays before reasoning about Tracktion's MIDI.
  - `LoopingMidiNode` ends the notes sounding at a clip's end, a sample early so the note-off isn't lost, and plays nothing after it, whatever the clip's sequence holds there. It keeps its sounding notes across a rebuild when only the clip's end changed (`hasSameContentAs` compares the start), so a clip can be lengthened or shortened under a held note. `EditSync::clipsEndBy` relies on both.
- **Play starts with the graph Tracktion has.** An Edit change asks for a rebuild on a 1 ms message-thread timer (`Edit::restartPlayback`), but `TransportControl::play` only builds a graph when none is allocated (`createPlayAudioNodesIfNeeded`). So a change made just before play is heard only once the timer fires, unless `edit.dispatchPendingUpdatesSynchronously()` builds it at once, as `EditSync::setClipsEnd` does. After a stop the context and its graph stay allocated, so only the first play of an Edit pays for making them.
- **Tracktion renders** (`Renderer::renderToFile`) stop all transports, and they need a non-empty track bitset (`toBitSet (getAllTracks (edit))`), whatever the docs say about empty meaning all. They also fail when nothing in the Edit makes a sound (no track with an instrument).
- **Tracktion's loop range reaches the playhead late, and clamped.** `TransportControl::setLoopRange` only stores the range; its timer passes it to the playhead every tenth tick at 50 Hz, and `PlayHead::setLoopRange` clamps a place past the new end to the end. `EditSync::updateLoop` passes it at once and wraps the place itself. Tests run no message loop, so without that the playhead would never get it.
- **Tracktion's playhead** (`tracktion_PlayHead.h`, step 6, part 3):
  - It counts in samples from where its place was last set, and while looping takes the remainder by the loop's length. A new loop length therefore moves the place unless the place is set again.
  - `setPosition` tells the players the playhead jumped only when the new place differs from what `getPosition()` says at that moment. They then end the notes sounding and strike those on at the new place. `overridePosition` never tells them, and clamps to the loop.
  - When the Edit's tempo map changes (its hash), the audio thread puts the playhead back on the beat its last block ended on, at the start of the next block (`checkForTempoSequenceChanges`, `tracktion_EditPlaybackContext.cpp`). So a place set on the message thread in between is overwritten, and a change of beat length (a time signature's denominator, with Tracktion's default `lengthOfOneBeatDependsOnTimeSignature`) would move it.
  - `TempoSetting::setBpm` remaps clips, the transport's loop and start, but not the playhead. It clamps to 20–300 BPM, so Hocket's top is 300 too.
  - Once a tempo setting has changed, the next `TempoSequence::toBeats` or `toTime` rebuilds the tempo map first (`updateTempoDataIfNeeded`). So read anything in the old tempo before changing the setting, and change it under the audio callback lock, where `syncTempo` reads the playhead's beat.
  - `TempoSetting::set` isn't cheap: its `CachedValue`s record an undo action, and every listener on the Edit's tree hears the change synchronously. About 20–35 µs as a rule, with a tail to tenths of a millisecond (step 6, part 5). It's the bulk of `syncTempo`'s hold of the lock.
- **Setting a Tracktion plugin's parameter:** set the `AutomatableParameter` itself (`masterLevel->setParameter (value, juce::sendNotificationSync)`), not only the `CachedValue` it's attached to (`masterLevelValue = value`). The stored value reaches the parameter the audio reads only through a ValueTree listener, so with no message loop between (the tests), the audio never hears it (found 2026-11-20 with 4OSC's trim).
- **Tracktion's volume plugins** (step 6, part 2):
  - Every new Edit's master is at −3 dB unless `Edit::Options::defaultMasterVolumedB` says otherwise. `EditSync` asks for 0 dB, and a render test in `MixTests.cpp` holds it there.
  - Automation writing is on by default (`AutomationRecordManager`); only a track's read mode stops a parameter change during playback from being recorded. What it records is flushed on a 10 Hz timer and committed when the transport stops, so a test of it must run the message loop.
  - `setPan()` rounds a pan under 0.005 to the centre, and dB below −100 is silence.
  - **It takes the mix as two parameters**, a fader and a pan, each an atomic the audio thread reads at the start of a block. Set one after the other, a block can start between them and head for a gain neither asks for (step 7, "Before 4b"). So Hocket leaves every track's at unity, set once when the track is made, and its own gain stage plays the mix. Anything that hands the audio thread several values that must change together needs them in one atomic, or one pointer to fixed settings.
- **After a jump, Tracktion strikes the notes sounding at the new place 0.1 ms late** (`LoopingMidiNode`, "so they come after controller updates"): 4 samples at 44.1 kHz. A note that starts exactly at a seek's position counts as sounding when the jump lands a rounding error after its start, so it comes 0.1 ms late too (step 7, part 4b). Tests of what a seek strikes allow for it.
- **A Tracktion MIDI clip keeps its playback node when moved**, and with it any sounding note, until its new start comes round. `EditSync` remakes a clip whose start or track changes.
- **Creating a JUCE audio device loads its driver.** `AudioIODeviceType::createDevice` returns a device that isn't open, but for ASIO the constructor loads and initialises the driver (`ASIOAudioIODevice` calls `openDevice()`). So asking a device for its rates and sizes isn't free: `--list-devices` only does it for the devices named, and the GUI's audio settings (Milestone 2) should only do it for the device being set up. WASAPI devices only query formats.
- **The device manager takes the nearest rate it can get.** Asked for a rate or buffer size the device doesn't offer, `AudioDeviceManager::setAudioDeviceSetup` opens at the nearest one it does offer without an error, and Tracktion then saves that for the next run. `openDevice` checks against the open device's lists first.
- **Custom Tracktion devices:** Tracktion lets a program register plugin types of its own with `PluginManager::createBuiltInType<T>()` (`tracktion_PluginManager.h:75`; the DemoRunner's `DistortionEffectDemo.h` is an example). Hocket's devices use it (Milestone 1's step 7 onwards).
- **Shell edits of C++ string literals.** In the Bash tool, `\\n` inside a heredoc can arrive as a real newline, and other backslashes in Python string literals get mangled too (Windows paths). Make code and doc edits with the Edit tool.
  - A heredoc whose text contains `\"` fails outright, even with a quoted delimiter: bash reports "unexpected EOF while looking for matching". For a scripted edit, write the script to the scratchpad with the Write tool and run it from there.
  - On 2026-11-17 a heredoc appending a page of C++ tests failed the same way with no `\"` in it (only `\n` escapes in string literals and apostrophes in comments). Don't append code with a heredoc: use the Edit tool, anchored on the file's last lines.
- **The PowerShell tool's working folder follows a Bash `cd`.** After a Bash command `cd`s into a subfolder (into `external/tracktion_engine` to read its source, say), `.\build\...` in the PowerShell tool fails with "not recognized as the name of a cmdlet". Start such PowerShell commands with `Set-Location D:\Projects\Hocket`, or use `git -C`/absolute paths in Bash.
- **doctest prints a `const char*` variable as `1`** in `MESSAGE` and `INFO` (a string literal prints fine). Wrap it in `std::string`, as with `typeid (x).name()`.
- **Windows port probes** (measured on this machine; used by `platform::isTcpPortFree`):
  - A socket with `SO_EXCLUSIVEADDRUSE` bound to 0.0.0.0 fails against any listener on the port: loopback with `SO_REUSEADDR` (like IXWebSocket), loopback plain, or wildcard. It succeeds when the port has only `TIME_WAIT` connections.
  - A plain bind to 127.0.0.1 misses wildcard listeners, and a plain bind to 0.0.0.0 misses loopback ones.
- **IXWebSocket's client always sends an `Origin` header** (`ws://host:port`) unless you set your own; it can't be left out. The server's web-page check accepts `ws://` and `wss://` origins for that reason.
- **IXWebSocket servers send in blocking mode** with no timeout by default; pass `sendTimeoutSeconds` (`Server.cpp` uses 2).
- **nlohmann `json` sorts object keys**; use `ordered_json` where order matters (the project writer does). The token file's keys come out alphabetical, which is fine.
- **Stopping a background `--play` cleanly from the tools.** A process started from the Bash or PowerShell tool can't be sent Ctrl+C, and killing it skips the clean exit.
  - Start it through `cmd /c` with `ProcessStartInfo.CreateNoWindow = true`: a console of its own, no window, output redirected to a file.
