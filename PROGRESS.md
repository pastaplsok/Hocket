## What exists
- `src/core` (`hocket_core`, no JUCE):
  - `notes/`: the `.notes` model, parser and canonical writer. A clip is at most 999 bars (`maxLengthInBars`). `Meter` is the time signature (numerator 1–32, denominator 2/4/8/16; ticks per beat, bar and sixteenths per beat), with `parseMeter`. `parse` and `write` take a drums track's `DrumMap` (names both ways, `drumNameProblem`, `nearestNames`, `standardDrumMap()`).
  - `project/`: the `project.json` model, reader, writer, and lookups like `findClip`, `notesOf`, `clipsUsing`, `tracksUsing` and `songEnd`. Each clip file's notes are kept once in `Project::notesFiles`, so linked clips share them. Tracks are `midi` or `drums`, with volume, pan, mute and solo; a drums track has a `drumMap` (`drumMapOf`, and `drumMapOfFile` for a file's), and a drum sampler a `kit`. `drumNameConflicts` says where a linked file's tracks would name its notes differently. A song ends by 1000.1 (`maxSongLengthInBars`). `load` can say before it reads each file (for stamps). `FileStamp`: a file's size and modified time.
  - `project/Rules`: the rules a valid project keeps, shared by the reader and the bus (step 4). `project/StrictJson`: strict JSON reading with each error at its place, for `project.json` and `kit.json`.
  - `kits/`: a kit's manifest, `kit.json` (`parseManifest`: pieces, levels, choke groups), and `KitCatalog`, the installed kits: bundled ones by name, the user's (Documents\Hocket\Kits) as `user/<folder>`, with why any kit folder can't be used; `refresh` for watched kits, and the load report. `WavHeader`: a sample's format from its header alone. The bus holds a catalog (`setKitCatalog`), which assigning a kit checks against.
  - `Suggestions`: `editDistance`, for "did you mean".
  - `units/`: values with units (`units::parse`/`format` for any `Quantity`; `units::volume()`), and pan (`parsePan`/`formatPan`).
  - `commands/CommandBus`: the only way to change a `project::Project`. Authors are `Author { name, session, label }`, compared by name + session. A command that changes nothing adds no entry. `interruptTransaction`, `openTransaction`, `changesTo` (the entries that changed a clip file's text: its notes, or how they're written); gestures merge into one entry (SPEC §3.1). It keeps the session's transport settings (`transportSettings()`: the loop region, loop on or off, the last seek), checks and words transport commands (`commands/Transport.h`, `TransportCommands.cpp`), and has the engine carry them out; `isPlaying()` asks it.
  - `commands/Commands.h`: the commands. `WriteClip`; `SetTempo`, `SetTimeSignature`; `AddTrack`, `RemoveTrack`, `RenameTrack`, `MoveTrack` (by a neighbour's ID), `SetMix`, `SetInstrument`, `SetDrumMap`; `AddClip` (empty, text, linked, copy), `MoveClip`, `RemoveClip`, `MakeClipUnique`; `Play`, `Stop`, `Seek`, `SetLoopRegion`, `ClearLoopRegion`, `SetLooping`. Values are written as project.json writes them.
  - `commands/Planning.h`: each command validated against the project and planned into edits (`SongCommands.cpp`, `TrackCommands.cpp`, `ClipCommands.cpp`). Errors start with what was being done ("add a clip: ..."). `AddTrack` and `SetInstrument` also take the kit catalog: a kit must be installed, and its names join the drum map (step 7, part 5).
  - `commands/Edits.h`: ten edits with exact inverses, which history entries keep. `commands/Changes.h`: change notices by ID, delivered once a command's edits have all applied.
  - `commands/WatchedSaves`: `--watch`'s clip file saves as the person's `write_clip` to the file's first clip, with a warning when one replaces a change made some other way since the file and its notes last matched (`matched`, which `WatchedFolder` sets from what Hocket last saved or read).
  - Saving (step 9): `CommandBus::save`, `hasUnsavedChanges` (history revisions) and `keptSaves`; `commands/Storage.h`, the interface `hocket_storage` implements, with `SaveResult` (what was written, moved and kept), `KeptSave`, `SaveInfo` and `describe`. `ReplaceProject` and `Revert` (`ProjectCommands.cpp`, and the bus's `planRevert`).
  - `Paths`: UTF-8 ⇄ path (`utf8FromPath` never throws: an unpaired UTF-16 surrogate becomes U+FFFD), `readTextFile`.
- `src/platform` (`hocket_platform`): `Platform.h` with `Platform_windows.cpp` / `Platform_posix.cpp`: the command line as UTF-8 (`utf8Arguments`, used by both programs), binary stdin/stdout, secure random bytes, process ID and program name, "is this program still running", `%LOCALAPPDATA%`, the Documents folder, the running program's folder, `FileLock` (one holder at a time; on Windows nothing else can even read the file), the TCP port probe, and saving's file writes: `writeFileToDisk` (flushed to disk), `replaceFile` (one step, write-through), `moveFile` (never over another file), each returning the OS's message on failure. The POSIX file has never been compiled.
- `src/storage` (`hocket_storage`, no JUCE; links core, platform and nlohmann): `ProjectFolder`, a project's folder and saving into it (SPEC §4.5): changed files only, refused when one changed outside Hocket (unless `overwrite`), all written beside their files before any is swapped in, the version on disk kept whole in `.hocket/saves/` first, a failed swap putting back the rest, `.hocket/save.json` saying who saved it, then clip files no clip uses moved to `unused/`. It knows each project file's stamp and text as Hocket last read or wrote it (`open`, `knownStamp`, `knownText`, `noteRead`). The list of kept saves, loading one, `keptSaveFolderName`. `createProject` for `--new`. `ProjectWatcher`: project files that differ on disk from what Hocket knows, once settled, project.json first, each reported once. `WatchedFolder`: `--watch`, taking them in as the person's commands. `SaveKeys`: `--play`'s `S` and `O` keys (step 9, part 5). `RecoveryCopy`, the recovery copy on disk, each one whole or not at all; `startRecovery` and `RecoveryKeeper`, what a session does with it (step 9, part 4). `Formats`: Windows-safe names and UTC times.
- `src/engine` (`hocket_engine`):
  - `EditSync` builds a Tracktion `Edit` from the bus's project in any time signature (the Edit's own stays 4/4, so Tracktion's beats are quarter notes; a 4OSC for each `hocket:synth`, Hocket's drum sampler for each `hocket:drum-sampler`, playing kits from the `KitLibrary` it's given), keeps its tracks, plugins and clips in step with the model by ID as tracks, instruments and clips are added, moved and removed (step 5), and is the bus's `Transport`: it plays the loop region or the whole song, on a loop or once (a 5 ms timer stops it at the end, and while a region plays once the Edit's clips end at its end, so nothing after it is heard), jumps on a seek, and wraps a playhead that's outside what plays into it, keeping its place in the bar. Each track's volume, pan, mute and solo are played by its gain stage, as both channels' gains (`syncMix`; step 6, and step 7's gain stage), ahead of Tracktion's volume plugin, which stays at unity; Tracktion's automation writing is off and the Edit's master at 0 dB, not Tracktion's −3 dB. A tempo change moves every clip to keep its beats, and the playhead's place and loop with it, under the audio callback lock (`syncTempo`, step 6), which it takes only through `AudioLock`, timing each hold (`longestAudioLockHold()`); a time signature moves nothing in time. Its clips don't use Tracktion's proxy sequences, so they play through `LoopingMidiNode`, which ends the notes a rewrite takes away (Gotchas). `stoppedByItself()` tells a stop Tracktion made from one a transport command asked for.
  - `mix/GainStage.h`, `mix/GainStagePlugin.h`: each track's mix as a gain on each channel, both handed to the audio thread in one atomic value and ramped together over 15 ms; the plugin, Hocket's first Tracktion plugin type, which `EditSync` puts on every track directly before Tracktion's volume plugin (step 7, before part 4b).
  - `devices/DrumSamplerPlugin.h`: the drum sampler as a Tracktion plugin (step 7, part 4b): MIDI read into hits without allocating, and its kit asked of the `KitLibrary` at the rate it plays at.
  - `devices/DrumVoices.h`, `devices/PlayableKit.h`: the drum sampler's real-time core (step 7, part 3): kits handed to the audio thread without locks and freed once no hit plays from them, a fixed pool of 64 voices, one-shot hits with choke groups and 10 ms fades, and `velocityGain`, the velocity curve.
  - `kits/KitLibrary.h`: kits loaded for the drum samplers on a loader thread, cached per sample file and rate, delivered by subscription on the message thread, with the user's kits in use watched (step 7, part 4a).
  - `kits/SampleRateConversion.h`: `convertSampleRate`, a kit's samples converted to the device's rate with Tracktion's libsamplerate, at its best quality (step 7, part 2).
  - `MasterOutput.h`: `--play`'s master level and output meter (SPEC §9), as Tracktion's global output processor, after the Edit; `describePeak` and `clippingWarning` for the end of a run. `defaultMasterVolume` is 0 dB (it was −15 dB until 2026-11-20).
  - `PlaybackDevice.h`:
    - `openDevice (DeviceChoice)`, from `--driver`, `--device`, `--sample-rate` and `--buffer-size`. It refuses a rate or size the device doesn't offer before changing anything, and catches a driver that carries on as it was. Errors suggest a name when exactly one contains the text given.
    - `listDevices` for `--list-devices`. Only the driver or device named has its rates and sizes listed, since that loads the driver. `formatNumbers` writes evenly spaced runs as ranges.
    - `PlaybackDevice`: what `--play` says about the device at the start and at Ctrl+C. It asks JUCE's device manager each time, since the manager deletes a device that disappears and opens another. The xrun report has the driver's count (where it keeps one) and JUCE's count of audio callbacks that took longer than their block.
- `src/api` (`hocket_api`, no JUCE): the WebSocket API (SPEC §6.3), its server and its client.
  - `Handler`: JSON-RPC in, reply out; `hello` with the token and the build check (error -32002 for another build); per-client state; interrupts on disconnect and in `checkIdle()`. It never throws: anything thrown while handling a request is answered with -32603.
  - `Protocol`: what both ends share: `protocolVersion` (bump it for changes to `hello` or the formats), `defaultIdleTimeout` (10 minutes), `hocketVersion()`, `buildFingerprint()` (FNV-1a of the protocol version and `toolDefinitions()`), and `makeSessionId()` for clients.
  - `Client`: a blocking IXWebSocket client, one request at a time; a late response to a timed-out request is dropped. Used by hocket-mcp and hocket-stress.
  - `Tools`: the 22 tools of SPEC §6.4 (step 10), their definitions (`readOnlyHint` on the four that read) and argument checks. The overview has the transport and output lines, each track's mix, devices and drum map (as changes to the standard map, which `write_clip`'s description lists), clips (a file only when the ID doesn't imply it), the kits in use with the names each plays, the installed kits, the history and whether anything is unsaved. `set_track` and `set_song` send several commands as one entry (`executeAsOne`); `patch_clip` uses `notes::patch`. On a drums track, `write_clip` and `patch_clip` list the notes the map doesn't name, and those the track's kit has no piece for.
  - `TextChanges`: write_clip's "stored differently" summary.
  - `Server`: IXWebSocket glue; posts every message to the message thread.
  - `TokenFile`: `api.json` read/write, `makeToken`, `runningInstance`, `instanceLockFile` (`api.lock`, next to it).
- `src/app` (`hocket-headless`): `--list-devices [--driver] [--device]`, `--check <folder>`, `--new <folder> [--user]`, `--play <folder> [--driver] [--device] [--sample-rate] [--buffer-size] [--master-volume] [--watch] [--user] [--recover | --discard-recovery]`, `--version` (with the API build). `--play`'s bus saves to the project's folder, on `S` in its console.
  - `--play` catches Ctrl+C from as soon as the project loads (before play, it stops with `stopped before playing`), takes `api.lock` first and holds it until it exits, makes the `KitLibrary` and waits for the kits in use before playing (`Loading kit ...`, `Loaded in ... ms`), serves the API, writes the token file, and runs a 50 ms timer. The timer says when playback stops by itself, calls `checkIdle()`, keeps the recovery copy up to date, and reads the keys typed. Exceptions in it are printed, not fatal.
  - `Console_windows.cpp` is the console's platform layer: UTF-8 output, Ctrl+C, closing the window (stops like Ctrl+C), QuickEdit off until exit, and the keys typed (`typedKeys`).
- `src/mcp` (`hocket_bridge` library, `hocket-mcp` program, no JUCE): the MCP bridge (SPEC §6.3).
  - `Bridge`: MCP JSON-RPC in, reply out. Answers `initialize`, `ping` and `tools/list` itself; forwards `tools/call`, re-reading the token file on every call. Takes the name from `clientInfo` (`claude-code` → "Claude") or `--name`, and the label from `--label` or the working folder. Adds a note to the first result after a restart, and says "Hocket isn't running" when it can't connect.
  - `Main.cpp`: the stdio loop (binary mode; skips blank lines, a trailing CR and a byte order mark), `--name`, `--label`, `--token-file`, `--version`. Logs go to stderr.
  - The `mcp` install component copies it to `<prefix>\bin`. A copy that's running is renamed aside first, and cleaned up by a later install.
- `docs/connecting-claude-code.md`: install, register, use, update, troubleshoot.
- `tools/stress` (`hocket_stress_client` library, `hocket-stress` program, no JUCE): Milestone 0's stress test over the API.
  - It rewrites one clip (`--clip`, default `clp-bass`) `--count` times (200) at `--rate` per second (20), then puts the clip's text back.
  - By default only a comment line changes, so the music shouldn't, and any click or gap is a glitch. `--vary` moves every other rewrite's notes up an octave.
  - It reports answer times (median, 95th percentile, slowest) and how far sends fell behind schedule. It exits 1 if any rewrite wasn't applied or the clip wasn't put back.

  - Change the tempo setting before taking the lock. But a listener to the setting may rebuild and swap in the new map itself, and an audio block could then run with the new map and the old loop, wrapping at the old loop's end; Tracktion's audio thread also moves the playhead to keep its beat when it sees a new map. Needs care, and a live test of a tempo change near the loop's end.
  - The `--play` exit report could include the longest hold, next to the late callbacks.
- **The Edit's time signature stays 4/4 (step 6, part 3).** Tracktion's beats are quarter notes and Hocket works out its own bars, so anything that reads the signature or the bar from Tracktion gets 4/4. Revisit before the first of: a metronome or count-in; one of Hocket's own devices that syncs to the bar (Milestones 4 and 5); VST3 hosting in Phase 2, since plugins read the time signature and bar position from the host (Lee, 2026-11-16; SPEC §8.2). [Claude's note: Tracktion's `EngineBehaviour::lengthOfOneBeatDependsOnTimeSignature()` returning false keeps its beats quarter notes whatever the signature, so the Edit could carry the song's signature without moving anything in time. Its audio thread would still put the playhead back on its beat when the signature changes (the Gotcha below), so a wrap made in the same instant needs the same care as the rare case below.]
- **A loop region played once, in Milestone 7** (step 6, part 4). While a region plays once, the Edit's clips end at its end (`EditSync::clipsEndBy`), so the stop's lateness is unheard: 10 to 16 ms in the real-time test, and `--play` on a real device will likely be later (bigger blocks, coarser timers). Audio clips will need to end there the same way, with a short fade so a cut waveform doesn't click.
  - The clamp is in Tracktion's graph before play starts and before a wrap into a new region. Turning loop off during playback within about a block of the region's end could still let the old graph reach past it, since the audio thread takes the new graph at its next block; not tested.
- **A wrap lost in one rare case (step 6, part 3).** When one batch of changes (an undo or rollback of a transaction) changes both the tempo and the song's end, and the song now ends before the playhead, `updateLoop` wraps the playhead after `syncTempo` has set the new tempo. Tracktion's audio thread then puts the playhead back on the beat its last block ended on (Gotchas, "Tracktion's playhead"), clamped to the new loop, so playback carries on from 1.1 instead of keeping its place in the bar. It needs a transaction holding a tempo change and a change to the song's end, undone during playback with the playhead in the part that went. Not handled.
- **Tracktion's undo** can't be fully off: JUCE keeps at least one step even at 0 levels, and some Tracktion setters (tempo, clip position) record into it. `EditSync` clears it after every sync; nothing ever undoes in the Edit.
  - Tracktion also records moves of its own there afterwards (found 2026-11-17): after clips are added, moved or resized, it sorts each track's clips by start on the message loop (`ClipOwner`'s async update, with the Edit's undo manager), and there's no public way to do it at once. They stay until `EditSync`'s next clear, at most a transaction or two, so it's harmless. The sync check allows child moves there and nothing else, since `EditSync`'s own changes are properties and children added or removed.
- **The slow `play()` in the engine tests: found and fixed (2026-11-13).** `play()` sometimes took about 2.5 s instead of 0.55 s, part-way through a run, on some days (2026-11-06, 2026-11-12, and the afternoon of 2026-11-13) and not others.
  - **Where:** a stack sample (the vs2026-symbols build, `HOCKET_TEST_SAMPLE_PLAY=1`) put 19 of 23 samples in `DeviceManager::addContext`, called from `EditPlaybackContext`'s constructor when play makes the playback context. It waits for the audio device to play a block, polling with `Thread::sleep (1)` up to 200 times.
  - **Why:** the tests play blocks themselves, after `play()`, so the poll always runs all 200 times, and takes 200 of the system timer's ticks. A 1 ms sleep took 1.2 to 1.7 ms in the fast plays and 9.3 to 10.2 ms in the slow ones, measured side by side. Windows 11 stops honouring a process's 1 ms timers when it isn't playing audio it can hear (power throttling), and the tests' fake device isn't heard; when that happens varies.
  - **Fix:** the engine tests ask for 1 ms timers at start and opt out of that throttling (`EngineTestMain.cpp`). Every `play()` then takes 0.54 to 0.72 s, and the engine suite about 100 s.
  - **Not the Magni or the MIDI outputs** (Lee's leads): the slowdown came back on 2026-11-13 with the Magni not connected, and the timer explains it. The Magni being connected on the earlier slow days was likely coincidence, or it changed how Windows throttled the process.
  - **Not a product problem, by reasoning, not measured:** in `--play` (and the GUI to come) a real device plays blocks all the time, so the poll ends within a block. Timing a real `--play` needs Lee's OK, since the saved device is ASIO4ALL, which takes the Magni from other audio.
  - **Kept for next time:** the engine tests warn when a `play()` takes over 1.5 s; `HOCKET_TEST_TIME_PLAY=1` prints each play's time and how long a 1 ms sleep really takes; `HOCKET_TEST_MIDI_OUTPUTS_OFF=1` disables Tracktion's MIDI outputs first; `HOCKET_TEST_SAMPLE_PLAY=1` samples the message thread's stack during each play (`StackSampler`; names need the vs2026-symbols preset's build). Tracktion's MIDI outputs are still on, as Lee asked.

- **`--watch`, and the save's outside-change check,** compare each file's modification time and size (`FileStamp`). A same-size rewrite within the file system's timestamp resolution could be missed, which is unlikely in practice.
- **`--play` at logoff or shutdown** (bug sweep, 2026-11-22; Lee: left for Milestone 2). JUCE loads user32, and Windows then never calls a console program's handler for logoff or shutdown, only for Ctrl+C, Ctrl+Break and closing the window. So `--play` ends without `RecoveryKeeper::finish()`, and changes from the last ~3 s (up to 30 s while they keep coming) aren't in the recovery copy. The fix is a hidden top-level window on the message thread that writes the copy on `WM_ENDSESSION`. The GUI app needs the same: JUCE's `systemRequestedQuit` only asks it to quit.
- **Milestone 2: an interrupted save that can't be finished is a choice in a dialog** (Lee, 2026-11-24). `--play` stops and prints why, where the version before the save is (the kept save) and the save's (the `.hocket-saving` files), the exact file to delete to go on, and what happens then. The GUI offers the same as a choice: go on without finishing it (Hocket removes `.hocket/saving.json` itself, sets the `.hocket-saving` files aside in `unused/`, and opens the files as they are); or don't open the project, showing where the two versions are; and, when a file was only held by another program, try again. `describeInterruptedSave` and `planFinish` already say which case it is.
- **Long paths where Windows' setting is off** (bug sweep, 2026-11-22): a project deeper than about 145 to 220 characters can't be saved there (refused, safely), since a kept save's paths pass 260. The manifest lifts that where the setting is on. Converting paths to the `\\?\` form would lift it everywhere; not done (Lee).
- **Saving to disk:** built in step 9 (`hocket_storage`). `S` and `O` in `--play`'s console are the person's way to save until the GUI; Claude's is MCP's `save`, in step 10.
- **Undoing a recovered entry files the recovery copy** (Lee, 2026-11-21; done). It used to remove it: after `--play --recover`, undo took the project back to its files, nothing was unsaved, and the copy went, leaving the recovered changes only in the redo list. Now `RecoveryKeeper` remembers the entry `--recover` made, and before the copy goes, unless those changes were saved (the entry still in the history and nothing unsaved), it files the copy with the kept saves as a discarded recovery, as `--discard-recovery` does, and says so: "The recovered changes aren't in the project any more, and were never saved, so the recovery copy written ... is filed as save #1, a discarded recovery copy, ...: revert brings them back." The same when they're put back by hand rather than undone, and at a clean exit. Once filed, it isn't filed again (a redo and a second undo remove the copy as usual); a copy that can't be filed stays, and filing is tried again every 10 s. Tests: 6 cases in `RecoveryTests.cpp` (and the crash test's ending), and a check in `Run-Acceptance.ps1`'s forced-kill run, passed on 2026-11-21.

Hocket works around or fixes each one itself instead.
  - The three Tracktion reports Claude drafted (the first MIDI scan, the dropped block, and `MidiNode`) stay unposted in Lee's `Documents\Hocket\upstream`, untouched, in case Lee decides otherwise. Anything posted would have to be in Lee's own words, per that policy.
  - Each time Tracktion is updated, DEPENDENCIES.md's "Updating Tracktion" checks whether the first three Tracktion items below are still needed.
  - **Tracktion, the dropped block:** `LockFreeMultiThreadedNodePlayer::prepareToPlay` calls `createThreads()`, which takes `processMutex`, for every graph rebuild, so the audio thread's `try_lock` sometimes fails and a whole block plays as silence (a 5.8 ms click, about once per 1,700 rebuilds). Fixed in Hocket's fork, kept long-term (DEPENDENCIES.md). How it was found: Gotchas, "Debugging Tracktion's playback".
  - **Tracktion, the first MIDI scan:** `DeviceManager::initialise()` calls `rescanMidiDeviceList()` (a 5 ms timer) and then `restartMidiCheckTimer()`, which replaces it with the 4 s rescan timer. So the first MIDI scan lands 4 s after startup and stops anything already playing. Workaround: `--play` runs the scan itself before playing (`src/app/Main.cpp`; Gotchas).
  - **Tracktion, `MidiNode`'s notes:** `MidiNode` (`tracktion_MidiNode.cpp`), which plays MIDI clips that use a proxy sequence (the default), keeps no note state across graph swaps.
    - `prepareToPlay` only checks whether the old graph had the node (54-60).
    - The new node then sends the new sequence's note-offs unchecked (171-197), and its loop-end note-offs come from that sequence too (201-205).
    - So a rewrite that changes a sounding note leaves the old one on for good. `LoopingMidiNode` gets this right.
    - Workaround: `EditSync` calls `setUsesProxy (false)` on each clip, so clips play through `LoopingMidiNode`. Repro: `hocket_engine_tests --test-case="stress: rewrites that change*"` with that call taken out.
  - **Tracktion, 4OSC allocates on the audio thread:** it builds a `juce::MidiBuffer` for every 32-sample sub-block (`FourOscPlugin::applyToBuffer`, `tracktion_FourOscPlugin.cpp:1484`), and `addEvent` allocates whenever a sub-block has MIDI. Noticed while chasing the stuck notes; no glitch traced to it. Hocket's synth replaces it in Milestone 4.
  - **Tracktion, `SamplerPlugin` locks and allocates on the audio thread:** `applyToBuffer` takes `lock`, a `CriticalSection` the message thread also takes (`tracktion_SamplerPlugin.cpp:297`), and creates a `new SampledNote` for every note-on (`:336`), deleted on the audio thread when it ends. Found while planning Milestone 1 (2026-11-06), so Hocket's drum sampler is its own from the start (SPEC §8.1).
  - **Tracktion, the version string:** `Engine::getVersion()` is hardcoded to "v3.1.0"; we read `VERSION.md` instead.
  - **IXWebSocket:** its server sets `SO_REUSEADDR` unconditionally (`IXSocketServer.cpp:135`), so on Windows a second server can bind a port another is listening on. `listen()` is non-virtual and the socket private, so `SO_EXCLUSIVEADDRUSE` can't be set without forking. Also, its server sends block with no timeout by default (`kSendTimeoutSeconds = -1`); `Server.cpp` sets 2 s.
